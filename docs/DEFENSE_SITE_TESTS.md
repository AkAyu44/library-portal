🖥 **Слайд 1 — Library Portal.**
💬 «Здравствуйте. Меня зовут Куат Бектурсын, группа IT1-2409IS. Я представляю итоговый проект по курсу
"Разработка веб-приложений на Spring". Это одно приложение — онлайн-каталог библиотеки, — в котором собраны
темы и индивидуальные варианты всех семи лабораторных работ».

🖥 **Слайд 2 — The idea: seven labs as seven layers.**
💬 «Главная идея: лабораторные работы — это не семь отдельных программ, а семь слоёв одной системы.
REST и MVC — это вход в приложение, IoC-контейнер его собирает, конфигурация задаёт параметры,
AOP добавляет сквозную логику — логи, аудит, замер времени, формы — это интерфейс для пользователя,
а седьмая лабораторная превращает API в документированный контракт.
В цифрах: семь лабораторных в одном приложении, семь индивидуальных вариантов, один общий сервис книг
и 32 автотеста — по тесту на каждый эксперимент из отчётов.
Технологии: Java 25, Spring Boot 4.1.1, Thymeleaf, валидация, Spring AOP, Actuator, HATEOAS и Swagger».

🖥 **Слайд 3 — Architecture.**
💬 «Так устроено приложение. Любой запрос сначала попадает в DispatcherServlet — это фронт-контроллер Spring MVC,
здесь же выбирается язык интерфейса. Дальше запрос идёт либо в REST-контроллеры, которые отдают JSON,
либо в страничный контроллер, который отдаёт HTML-страницу. Ошибки обрабатываются в одном месте.
Ниже — сервис книг. Spring обернул его прокси-объектом, и каждый вызов проходит через четыре аспекта.
Сам сервис работает с хранилищем книг, отправляет уведомления и кэширует цитаты.
Зелёные кружки показывают, из какой лабораторной каждый блок».

🖥 **Слайд 4 — Лаба 1, Spring Boot и первый REST-контроллер.**
💬 «Первая лабораторная — создание проекта на Spring Boot и первый REST-контроллер.
Из неё в проекте остались структура Maven-проекта и контроллер с адресами /api/hello и /api/info.
Мой вариант 7 — подсчёт слов: адрес /api/wordcount возвращает количество слов, символов и самое длинное слово.
Если текст не передан, возвращаются нули, а не ошибка».

🖥 **Слайд 5 — Лаба 2, IoC-контейнер.**
💬 «Вторая лабораторная — контейнер Spring и внедрение зависимостей. Есть четыре способа отправить уведомление —
консоль, email, HTML и пустой. Spring сам выбирает нужный: email помечен как основной, порядок списка задаётся
аннотацией @Order. Также показаны жизненный цикл бина и разница между singleton и prototype.
Мой вариант 8 — HTML-уведомление, которое экранирует угловые скобки, чтобы текст не выполнился как HTML.
В проекте это работает по-настоящему: при добавлении книги отправляется уведомление».

🖥 **Слайд 6 — Лаба 3, конфигурация.**
💬 «Третья лабораторная — настройки приложения. Они вынесены в YAML-файлы, для режима разработки dev
и боевого режима prod есть свои файлы. Таблица слева показывает, как меняются значения: в dev другой порт,
отключена почта и короче кэш. Настройки проверяются при запуске — с неверным значением приложение не стартует.
Внизу — порядок приоритета: аргумент командной строки сильнее всех остальных источников.
Мой вариант 7 — настройки кэша, и в проекте они реально управляют кэшем цитат».

🖥 **Слайд 7 — Лаба 4, Spring AOP.**
💬 «Четвёртая лабораторная — аспектно-ориентированное программирование. Логирование, аудит, замер времени
выполняются не внутри методов, а в отдельных аспектах. На схеме видно, как они вложены друг в друга:
снаружи аудит, затем лог, затем таймер. Справа — реальный лог из приложения.
Отдельный эксперимент — самовызов: если метод вызывает другой метод того же объекта напрямую,
аспекты не срабатывают — 0 записей аудита; через ссылку на прокси — срабатывают, 2 записи.
Мой вариант 8 — трассировка вызовов: отступ в логе показывает вложенность».

🖥 **Слайд 8 — Лаба 5, Spring MVC.**
💬 «Пятая лабораторная — Spring MVC. Её выполнял мой напарник Бекбаев Гибрат, а в проекте она стала основой каталога.
Здесь REST API для книг и HTML-страница каталога. Главный эксперимент — коды ответов:
каждый код говорит, что именно не так с запросом. 200, 201, 204 — успех;
400 — неверный параметр, 404 — нет ресурса, 405 — не тот метод, 415 — не тот формат тела, 406 — не тот формат ответа.
Вариант 6 — библиографическая ссылка на книгу простым текстом».

🖥 **Слайд 9 — Лаба 6, формы и валидация.**
💬 «Шестая лабораторная — формы. Вверху путь сообщения об ошибке: браузер отправляет форму, Spring заполняет объект,
валидатор проверяет поля, текст ошибки берётся на нужном языке и показывается рядом с полем.
Интерфейс работает на английском и русском. Есть своё правило проверки — имя автора без цифр,
и отдельные страницы ошибок для сайта и для API.
Мой вариант 7 — дата публикации: она не может быть в будущем, а её формат зависит от языка».

🖥 **Слайд 10 — Лаба 7, REST API: DTO, коды ответов и ошибки.**
💬 «Седьмая лабораторная — превратить API в такой, которым может пользоваться другая команда.
Вверху — путь данных: клиент присылает запрос, маппер превращает его в книгу, а ответ строится обратно отдельным объектом.
Клиент не может сам задать номер книги или дату создания — их назначает сервер.
В таблице каждый результат имеет свой код: создание — 201 и адрес новой книги, удаление — 204,
нет книги — 404, в том числе при повторном удалении, а дубликат — 409.
Справа — пример ошибки 409 в стандартном формате RFC 9457. Все ошибки формируются в одном месте».

🖥 **Слайд 11 — OpenAPI, Swagger UI и HATEOAS.**
💬 «Документация API генерируется автоматически: страница Swagger показывает все операции, и их можно
выполнить прямо из браузера. На скриншоте — запрос несуществующей книги и ответ 404 внутри Swagger.

В боевом режиме Swagger отключён, потому что открытая документация небезопасна.
Мой вариант 7 — HATEOAS: ответ о книге содержит ссылки — на саму книгу, на весь каталог и на её цитату».

🖥 **Слайд 12 — Как связаны лабораторные.**
💬 «Главное отличие проекта от набора лабораторных — связи между ними. Добавление книги отправляет уведомление

Ошибка клиента теперь возвращает 400, а не 500, как было в лабе 4».

## Шаг 7. Лаба 7 — Swagger UI (главная часть)
🌐 вкладка `http://localhost:8080/swagger-ui.html`
💬 «Лаба 7. Это документация API, сгенерированная автоматически. Группа Books — все операции с книгами,
у каждой описание».

**7.1. Список и одна книга (HATEOAS)**
👉 Раскрыть **GET /api/books** → **Try it out** → **Execute**.
💬 «Список книг — код 200, JSON-массив».
👉 Раскрыть **GET /api/books/{id}** → **Try it out** → id `1` → **Execute**.
💬 «Одна книга — и мой вариант 7: в ответе блок _links со ссылками на саму книгу, каталог и цитату. Это HATEOAS».

**7.2. Создание — 201**
👉 Раскрыть **POST /api/books** → **Try it out** (пример книги уже заполнен) → **Execute**.
👉 Показать: **Code 201**, в **Response headers** строка `location: /api/books/6`
(номер 6, потому что книга номер 5 уже добавлена через форму в шаге 6; запомнить номер из location).
💬 «Создание — 201 Created, и заголовок Location с адресом новой книги. Номер и дату создания назначил сервер».

**7.3. Дубликат — 409**
👉 Ещё раз **Execute** в том же POST.
💬 «Та же книга второй раз — 409 Conflict. Это не ошибка формата, а конфликт с тем, что уже есть в каталоге.
Ответ в стандартном формате ошибок».

**7.4. Невалидные данные — 400**
👉 В теле POST стереть название: `"title": ""` → **Execute**.
💬 «Пустое название — 400, и в поле errors видно, какое поле неверно и почему».

**7.5. Удаление дважды — 204, потом 404**
👉 Раскрыть **DELETE /api/books/{id}** → **Try it out** → id `6` (номер из location) → **Execute** → **Code 204**.
👉 Ещё раз **Execute** → **Code 404**.
💬 «Первое удаление — 204, удалено. Повторное — 404: книги уже нет. Состояние сервера не меняется,
поэтому удаление остаётся идемпотентным, а клиент узнаёт, что удалять было нечего».

**7.6. Нет книги — 404 с пятью полями**
👉 **GET /api/books/{id}** → id `999` → **Execute**.
💬 «404 в формате RFC 9457, тип application/problem+json. Пять полей: type, title, status, detail, instance.
Стектрейса в ответе нет — он остаётся в логах сервера».

**7.7. Документ OpenAPI**
👉 Вверху страницы Swagger нажать ссылку `/v3/api-docs` → **Ctrl+F** → `maxLength`.
💬 «Это сам документ API. maxLength 120 у названия взялся из правила проверки в коде.
В боевом режиме prod Swagger отключён — тест это проверяет».

## Шаг 8. Лаба 4 — аспекты (в конце, потому что удаляет книги)
🌐 Главная → карточка Lab 4 → `/api/system/proxy` → назад.
💬 «Сервис книг — это прокси, который Spring создал сам: в имени класса SpringCGLIB».
👉 `/api/books/stats` (ответ придёт с задержкой ~0,3 с).
👉 Переключиться в IntelliJ, внизу вкладка **Run** (консоль) — показать строки `[AUDIT]`, `[LOG]`, `[TRACE]`, `[TIME] SLOW`.
💬 «Каждый вызов сервиса проходит через аспекты: аудит, лог, трассировку и таймер.
Этот метод работает 300 мс, поэтому таймер пишет SLOW».
👉 Swagger → группа **system-controller** → **DELETE /api/system/audit** → Try it out → Execute (очистить аудит).
👉 Swagger → **DELETE /api/books/bulk** → Try it out → в поле **ids** нажать **Add integer item** и ввести `3`,
viaProxy выбрать `false` → **Execute**.
👉 Ещё раз: ids `4`, viaProxy `true` → **Execute**.
🌐 открыть `http://localhost:8080/api/system/audit`.
💬 «Эксперимент самовызова: при viaProxy=false метод вызывает удаление напрямую, мимо прокси,
и аудит не записался. При viaProxy=true вызов идёт через прокси — аудит есть.
В журнале только одна запись BOOK_DELETE — для книги номер 4».

## Если что-то пошло не так
| Ситуация | Что делать |
|----------|-----------|
| POST в Swagger сразу 409 | Книга уже создавалась — объяснить 409; для 201 изменить title в теле |
| DELETE даёт 404 сразу | Посмотреть номер в `location` после POST и удалить именно его |
| Whitelabel Error на главной | Запущена старая лаба — остановить ■, запустить `LibraryPortalApplication` |
| Нет Swagger или старый дизайн | Maven → ⟳ Reload, перезапуск, в браузере Ctrl+F5 |
